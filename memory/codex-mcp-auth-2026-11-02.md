The Codex config uses the serialized helper (`http_headers_helper` = ~/.local/share/atoma-codex-auth/auth.py headers, docs/codex-mcp-connection.md). Helper `status` showed phase "renewing", expires_at 2026-10-31 12:08:56 UTC; Keychain item run.atoma.codex-oauth.v1 mdat 2026-10-31 15:05:10 UTC. The Codex desktop log (~/Library/Logs/com.openai.codex/2026/10/31/*000015-0.log line ~6046) shows at 15:05:40 "MCP HTTP headers helper timed out after 10 seconds" with authStatus=oAuth (native stored credentials present too). nginx shows NO /oauth/token from atoma-codex-auth/1 after 11:08:57 that day, while the Mac was online: the renewal request never reached the server; the helper discards its error (detached worker, stdio to /dev/null), so the exact cause is unknown. Since then every helper call fails closed, and `codex mcp login` cannot even run discovery. Codex desktop 0.165 also keeps refreshing its own native atoma tokens (10-31 19:46, 11-01 06:30/08:16, 11-02 10:30 UTC).

Root cause class: `src/auth/mcpOAuthStore.ts` refresh() revokes the whole grant on ANY refresh-token reuse (no grace). platform_events token.revoked reason refresh_token_reuse since 2026-10-01: chatgpt.com Codex client 38 (last 10-27), claude.ai claude-code client 4 (last 10-31 10:51, which disconnected the atoma MCP in my Claude Code session). The helper was a Codex-only client-side workaround; it fails closed on any uncertain renewal and needs a browser login each time.

**Why:** the owner reported it as "solved twice"; both fixes were client-side.
**How to apply:** immediate unblock = helper `login` (browser consent), then `codex mcp logout atoma`, restart Codex, check helper `status` = ready; never run `headers` visibly; never `codex mcp login atoma` while the helper is configured. Durable fix proposed to the owner (pending go): a short server-side refresh reuse grace (same client, seconds-long window) so racing or lost refreshes do not revoke grants, then retire the helper; plus helper failure logging without secrets. Needs adversarial review + prod deploy. Related: [[mcp-one-surface]], [[prod-ssh-authorized]].

**Fixed 2026-11-02 (owner said "Oui fait le"):** commit 9677f478 on main, CI + CodeQL + deploy green, host on release 9677f478 since 12:51:34 UTC, auth_mcp_refresh migrated (used_at, successor, rotated_from, replays). Design: a rotation seals the issued pair under HKDF(consumed refresh token) with AES-256-GCM (grant id AAD) and records sha256 of the caller's /24 (/64); the same client from the same network within 120 s gets the grant's CURRENT pair (chain walk, every hop must be the same network, max 32 hops else revoke `refresh_chain_exhausted`); first replay per token journaled `token.refresh_replayed` (security, no push); elsewhere/later reuse revokes as before. The first adversarial review found the unbounded grace let thief and client co-exist forever → network binding added; production verified ATOMA_VIZ_TRUSTED_PROXIES=127.0.0.1,::1 and nginx `proxy_set_header X-Forwarded-For $remote_addr` (binding depends on both). Local: ~/.codex/config.toml http_headers_helper removed (backup ~/.codex/config.toml.before-native-oauth-20261102); `codex mcp list` then showed atoma "Not logged in" → owner must run `codex mcp login atoma`. Helper's stranded grant expires ~2026-11-22 (or revoke in token settings). To check later: platform_events kinds token.refresh_replayed vs token.revoked reason refresh_token_reuse.
