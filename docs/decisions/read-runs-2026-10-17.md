# Reading other runs' saved files ("read runs") — decision and contract, 2026-10-17

Status: BUILT, then corrected after three adversarial reviews the same day
(security, lifecycle, the text models read; [below](#review-2026-10-17)) and
a second pass over the fixes ([below](#second-review-2026-10-17)) and a
third check of those ([below](#third-check-2026-10-17)). A
run can now read the saved files of up to three other runs of its project,
named by the client, as copies in its workspace with their saved modes.
Before this, a run could read the files of exactly one other run: the one it
was seeded from. The project conversation proposes them too, since the same
day ([below](#read-runs-from-the-conversation-2026-10-17)).

## The incident

Attica run `2e6bdcfc` (2026-10-16, partial, $4.58) was seeded from run
`8402ca88`, which was also its `baseRunId`. Its first goal item asked it to
"restore browser/collect-xe-browser.js, browser/control-server.js,
tests/xe-browser-local-hardening.test.js and tests/xe-browser-integration.test.js
to exactly the bytes they had in the starting delivery of the previous run
(run 50019ee0)".

- A discovery branch searched the workspace for `50019ee0`, history or a
  baseline, and found nothing. The ground truth said there was no `.git`.
- The branch reported that no materials it could reach held the files of run
  `50019ee0`. The result's `c1_blocker` said the same.
- The root acceptor refused c1: no evidence compared the four files with run
  `50019ee0`. It refused c4 for the same reason ("unchanged" with nothing to
  compare against).

The workaround does not scale. Run `760fef4c` ($7.67) spent 1,232 of its
2,829 goal characters on hand-written edits and two target sha256 values;
`4d330cc5` carried the same kind of text. Goals stop at 4,000 characters, and
`collect-xe-browser.js` alone is 19,412 bytes.

It is rare: of the 378 production project runs, 7 goals named a run of the
same project other than their seed, all in Attica, and only `2e6bdcfc` needed
that run's bytes. But it makes a whole kind of criterion impossible rather
than costly: "restore to, or compare with, the bytes of run X".

Sizing, over the 316 saved manifests: p95 3.2 MB; the largest 44.8 MB and
1,502 files; none above 64 MiB. Attica's are about 3.6 MB and 148 files, in a
113 MB workspace.

## The contract, as built

- **The request.** `readRunIds` on a new run (`createProjectRunInputSchema`):
  one to three distinct ids. Each must be what `baseRunId` must be
  (`ProjectStore.iterationBase`): the same organisation and project, delivered
  or partial, not a comparison rerun, bytes not expired, a saved manifest. The
  saved files of all of them together are at most 64 MiB and 10,000 files,
  refused over either and never trimmed; both caps read the saved manifests,
  so a refusal hashes nothing. The seed run itself may be named: a pristine
  copy for an "unchanged" claim. MCP: `atoma_run_start.readRunIds`; the HTTP
  route takes it through the same schema.
- **Admission.** The coordinator checks every id and re-reads every saved
  file against its manifest (`revalidateArtifactManifest`) before it reserves
  anything; the store checks the rule again inside the reservation
  transaction. A refusal is a 409 naming the run.
- **Identity.** The list is stored sorted (`project_runs.read_run_ids_json`),
  immutable by trigger, and part of both request-identity comparisons: the
  same key with other read runs is a conflict, and a live identical request
  re-attaches only when it reads the same runs.
- **Reruns and continuations.** A comparison rerun reads what its origin read
  (copied by the store), refused when one of them expired: a rerun with fewer
  inputs would compare two different requests. A continuation reads what its
  source read and keeps the copies its sealed workspace already holds; its
  index carries the stored manifests, so their bytes may have expired since.
  `resumeOf` with `readRunIds` is refused, as with `baseRunId`. A run started
  again after a GitHub access interruption keeps its list.
- **Launch.** The coordinator re-checks the bytes (a byte changed while the
  run queued refuses it before spawn) and writes `<runRoot>/read-runs.json`:
  mode 0600, outside the workspace, removed with the run. It holds the
  organisation, project and run, and per read run its id, status, end time,
  workspace path, manifest hash and manifest. `ATOMA_READ_RUNS` names the
  file: 1,502 manifest entries exceed Linux's 128 KiB bound on one
  environment string.
- **The run process.** It reads the variable once, removes it from its
  environment, and refuses it outside a tenant project run, for another run,
  or for another organisation or project (the connectors' pattern). It
  re-hashes every manifest. After the seed copy, at launch and again at a
  deepening's restart, it copies every manifest entry through
  `readManifestArtifact` (O_NOFOLLOW, identity, size, mode and sha256) into
  `<workspace>/.atoma-runs/<runId>/<path>` as a new file with its SAVED mode:
  0755 for a `100755` entry, 0644 otherwise. It keeps the identity (device,
  inode, ctime, mode) of each copied file and of each directory, `.atoma-runs`
  included, with the names it holds, and takes them again after a
  continuation's checkpoint restore, which re-creates the files. A mismatch at
  launch is a `RunnerConfigError` before any model call; at the restart it
  fails the run with the first attempt intact in `.prevN`, as a seed that
  cannot be copied does. That archive does not keep the copies: it is made
  first, then they are removed from it at best (every directory given u+rwx
  first, no link followed, a logged line on failure, never a failed
  restart), and copied again into the new attempt.
- **Never mounted, never linked.** The worker still mounts only the
  workspace. The other run's directory is read by the run process on the
  host and is not reachable from the container, by any path.
- **Never inherited or delivered.** `.atoma-runs` is an `.atoma-*` path, so
  the inventory, publication, preview and retrieval corpus already leave it
  out (`assertPublishableArtifactPath`). `seedWorkspace` leaves out the seed's
  top-level `.atoma-runs`. `inheritProbeManifest` drops an entry that reaches
  INTO a copy: a path naming a run id (`.atoma-runs/<run id>/…`) in anything a
  replay runs or compares (a shell command or its recorded output, a web
  entry's page, smoke or interactions, an http entry's host-stamped server
  `entry`, request path or body; never its free-text `note`), and in a
  command also a glob where the id would be (`diff -q x.js
  .atoma-runs/*/x.js`) or a shell entering the directory (`cd .atoma-runs`).
  It can be replayed only where the copy existed. A command that leaves the
  copies out is kept: an exclusion option's argument (`--ignore-pattern
  '.atoma-runs/**'`, `--exclude '**/.atoma-runs/**'`, `zip -x`, `fd -E`), a
  `!` glob, bare or as an option's value (`--glob='!…'`), a git pathspec
  excluding it (`':!…'`, `':(exclude)…'`), a negated or pruned `find -path`,
  a group of paths included. A variable holding the directory (`D=.atoma-runs;
  cat $D/…`) is out of reach of any reader of the command string, and kept.
  That is an inheritance rule, never a malformation, so the health check does
  not report it. The preview never picks a server entry under an `.atoma-*` directory
  (the stamp before it, then the fallbacks), and `atoma-scaffold` reads a
  directory holding only `.atoma-*` entries as empty. Parent-owned test
  snapshots skip the directory, so a suite never copies the reference bytes,
  and a suite that names `.atoma-runs` is refused at plan time.
- **What the models read.** One task input, `readRuns`, one item per read run
  (`runId`, `path`, `status`, `endedAt`, `files`, `bytes`), and one sentence
  beside it. It is host-owned like `previousRunResults`: stripped from
  `originalTask` copies, never replaceable by a plan's child inputs, and
  replaced, never appended, on resume. L1 compares and copies with `cp`,
  `diff` and `sha256sum`, on the default shell allowlist; `cmp` is not on it
  and works only through `bash -c`.
- **Integrity.** A copy's mode is not read-only: a 0444 copy made every file
  restored from it with `cp` read-only and dropped the executable bit, and a
  mode never stops the workspace's owner's shell. `write_file` and
  `edit_file` refuse a path that lands under `.atoma-runs/` (links followed,
  the directory's name read case-blind), and so does `atoma-scaffold`'s
  target: a restore copies FROM a copy. A shell is not refused, so a change
  to a copy is DETECTED. Before each root acceptance the host checks every
  copy against its manifest (bytes AND mode) and against the identities it
  kept: a saved file changed or missing, one changed and put back (its bytes
  equal again, its ctime moved, which userspace cannot reset), a directory
  moved or modified with its names unchanged (a whole copy swapped aside and
  back), and names added inside it, a separate fact. The acceptor reads one
  host line per read run, in the holistic and the focused criteria review.
  It also reads one host line per saved path of a read run that the criteria
  name: the manifest's own paths, spelled out in the criteria text, found at
  a path boundary (a leading `./` or `/` accepted; a stem such as "todo" is
  never a mention), at most 16; this run's file, read on the host (never through the model-facing
  `read_file`, which would disarm `write_file`'s blind-overwrite refusal),
  against the saved entry's sha256 and mode, identical or differing. The
  criteria read-back never reads a copy. Facts beside the judgement; they
  decide nothing on their own.
- **Retention and removal.** ONE predicate says whether a run can still be
  continued (`projectRunContinuable`: paused, or interrupted and
  recoverable; a cancelled run whose checkpoint row stayed 'running', and a
  blocked one, cannot). A run named by a reader that is queued, running or
  continuable is held (`active read run`), read on the plan's read-only
  handle. Copies are removed: when their run ends and cannot be continued,
  after its manifest and preview descriptor are built; a paused run's when
  the continuation that consumed its checkpoint ends; a run failed by a
  server restart's at the next boot, with the run it continued, unless
  continuable; and from a deepening's archive. Each removal gives every
  directory u+rwx first, follows no link, logs a line when it fails and never
  fails anything. A released run also loses the copies its checkpoint
  snapshot sealed into the product store (`forgetReadRunCopies`), unless
  another run that can still be continued restores from that snapshot.

## Text the models read

About 4 characters per token.

- Guidance, about 165 tokens (659 characters), only when `readRuns` is
  present, in every planning, validation and execution prompt of that run
  (`READ_RUNS_GUIDANCE`, pinned by a test). It says nothing of later runs but
  what holds for all: no delivery and no seed carries them.
  "readRuns are copies of other runs' saved files, chosen by the client; the
  host never delivers them or seeds them into the next run. Leave them in
  place and unchanged; read, compare or copy from them as the task asks. Parent-owned
  suites cannot read them: prove a restore or comparison with sha256sum or
  diff in a shell step (the host also compares the files the criteria name at
  acceptance). A check run inside them proves nothing about this run's files.
  Run a tool that walks the whole tree (eslint ., a test runner's default
  include) on a copy of the workspace without .atoma-runs rather than change
  the project's configuration, unless the task allows that."
- The input, about 51 tokens per read run, in the same prompts:
  `{"readRuns":[{"runId":"50019ee0-…","path":".atoma-runs/50019ee0-…","status":"partial","endedAt":"…","files":148,"bytes":3629836}]}`.
  About 32k extra input tokens for a 150-call run with one read run (the call
  count is an assumption; most of it is cache-read).
- The acceptor's lines, root acceptance only. Per read run, about 42 tokens
  intact, 62 changed and put back, more with the paths named:
  "READ RUN COPY (host-checked): .atoma-runs/<runId>/ still holds the <N>
  saved files of run <id8> byte for byte, with their saved modes.", "… holds
  the <N> saved files of run <id8> byte for byte now, but "<path>" was changed
  after the copy: a comparison made meanwhile may be wrong." or "… NO LONGER
  matches the saved files of run <id8> (changed (bytes or mode): …; missing:
  …; changed after the copy, equal again: …). A comparison with this copy
  proves nothing about that run." Names the run added follow as their own
  sentence and never make a line say "proves nothing". Per criteria-named path
  a read run saved, at most 16, about 32 tokens: "READ RUN FILE
  (host-checked): "<path>" here is identical to run <id8>'s saved file (bytes
  and mode)." or "… differs from run <id8>'s saved file (bytes; mode 100644
  here, 100755 saved)." At most ten paths per kind, each JSON-encoded, so a
  name the run chose cannot print a line of its own.
- A parent suite naming `.atoma-runs` is refused at plan time with zero
  tokens, in the precheck's one refusal: a parent-owned suite cannot read it,
  so remove the mention and prove the comparison in a shell subtask (the host
  also compares at acceptance). Never "can never pass": a suite that only
  excludes the directory passes, and removing the mention is enough. Any
  mention is refused: narrowed to an id, `join('.atoma-runs', id)` passes.
- `write_file`, `edit_file` and `atoma-scaffold` into a copy answer, at no
  cost: "refuse to write into .atoma-runs/, the copies of other runs' saved
  files, which stay unchanged. To restore a file, copy it FROM its copy (run_shell
  cp .atoma-runs/<run id>/<path> <path>), or read it and write the workspace
  path. Nothing was written."
- The MCP parameter, about 147 tokens in `tools/list` for member tiers and
  above: the caps, "copied with their modes", "never delivered, published or
  seeded into the next run (a comparison rerun or continuation reads the same
  runs again)", that the host compares each file a criterion names, and "Not
  with rerunOf or resumeOf".

## Rejected

- **(a) Pasting bytes into the goal.** The 4,000-character cap, and
  transcription errors.
- **(b) A host element `read_run_file`.** A new immutable wire contract,
  persisted in the shared registry; bytes would pass through model-written
  JSON, be truncated, exclude binary files, and allow no `cp` or `cmp`.
- **(c) A second container mount.** It breaks "only the workspace" and the
  `read_file` jail.
- **(d) A nested read-only bind mount at `/workspace/.atoma-runs`.** The
  kernel would enforce read-only, but it needs launcher and remote-worker
  support, host-side readers would see an empty mount point, and a resume
  would have to remount. Kept as hardening if tampering is ever observed.
- **(e) Copying whole workspaces.** 113 MB instead of 3.6 MB, no byte
  identity outside the manifest, and it would bring another run's
  `.atoma-probes.json` and secrets.
- **(f) Failed or cancelled runs.** No manifest, and no observed need.
- **(g) Inferring ids from the goal text.** A regular expression over tenant
  text would decide control flow.
- **(h) Links into the other workspace.** A write path into another run's
  evidence: the hard-linked-seed hazard repository sync already guards
  against.
- **(i) Read runs as a second seed.** "A seed says where the workspace came
  from, never why" (src/run). Read runs change nothing about depth,
  comparison status, seeding, landing or previous-results context.
- **(j) The name `referenceRunIds`.** It collides with
  `acceptedReferenceRunId`, which names a version to start from.
- **(k) Read-only (0444) copies** (built, then reverted the same day). `cp`
  gives a new file its source's bits: every file restored from a copy was
  read-only (`edit_file` failed EACCES, and the next run's seed copy kept
  0444) and a saved script lost its executable bit while `sha256sum` still
  matched. The mode never stopped the workspace's owner anyway.
- **(l) Dropping an inherited entry on any mention of `.atoma-runs`.** It
  dropped the exclusions the guidance asked for (`--ignore-pattern
  '.atoma-runs/**'`), and with them a seeded run's lint replay.
- **(m) Refusing a continuation once a read run expired.** The hold keeps the
  read run instead while its reader can still be continued.
- **(n) Two readings of "can still be continued".** The hold read any
  unfinished checkpoint row, the removal paused or recoverable: a cancelled
  or crashed reader held its read runs for 90 days with nothing able to read
  them. One predicate now.
- **(o) Stamping a recipe whose compile example names a copy.** The path came
  from this run's subtask, not the recipe; a stamp kept a later clean example
  from compiling. Postponed without a stamp, as a Decision "no" is.

## Risks that remain

- The acceptance contract said "probes cannot reach another run"
  ([acceptance contract](acceptance-contract-2026-09-14.md)). These are
  copies the client chose, checked against immutable manifests, with no path
  back into the other workspace.
- **Forged proof, narrowed.** The write tools refuse a copy; a shell can
  still change one (detected, not prevented). A change put back is reported
  by its moved ctime, a swapped directory by its own, and the host compares
  the files the criteria name with the saved entries, which no model can
  write. Left: phase validators read neither line, so a phase approved on a
  forged comparison earns its trust and lessons before the root reads it;
  `touch` or a no-op `chmod` on a copy reads as a change; a directory swap
  combined with a name added at that level reads only as the added name; a
  hard link made to a copy from elsewhere lets `write_file` change it under
  the other name (reported, by its ctime); a continuation takes the
  identities again, so a change made and put back in an earlier segment is
  not seen; a path the criteria do not spell is not compared.
- **Scope.** The organisation and project are checked in the reservation
  transaction and again in the run process. Members can already read these
  files through `atoma_run_file`, so no new authority is granted; secret-like
  names never enter a manifest, so this is stricter than seeding.
- **Tooling.** A project whose lint or test globs walk dot directories checks
  the old code. Verified on 2026-10-17: ESLint 10's flat config lints
  `.atoma-runs/**`, and the skeleton's typed lint then fails `npm run check`
  on a copy outside its tsconfig ("parserOptions.project has been provided");
  Vitest's DEFAULT include also runs a copy's old tests, while an explicit
  `include` such as the skeleton's or Attica's `tests/**` does not. Application
  skeleton v2 ignores `.atoma-*/**` in ESLint, which also covers
  `.atoma-skeleton` and `.atoma-scratch`; `application:skeleton:smoke` runs
  `npm run check` beside a copy that fails typecheck, lint and tests (it fails
  without the ignore). Older projects get the guidance, which asks for such a
  tool to run on a copy of the workspace without `.atoma-runs` rather than in
  a changed configuration (`APPLICATION_TYPESCRIPT_GUIDANCE` forbids hiding
  source).
- **Copies left behind.** A run that stays paused, never continued, keeps
  its copies, in its workspace and its snapshot, and holds its read runs,
  until its own retention: it can still be continued. A run failed by a
  server restart loses its copies at the next boot even if an orphaned
  process of it still runs; its results are discarded anyway, and a
  recoverable checkpoint restores from its sealed snapshot. A removal that
  fails (a copy owned by another user) leaves a logged line and the bytes.
  Rows deleted from the product store stay in its free pages until reused,
  and in backups taken before.
- **Cost.** Up to 64 MiB and 10,000 files of extra disk per run while it can
  run or be continued, plus checkpoints, which seal the copies; synchronous
  hashing at admission and launch, as `baseRunId` already does, now bounded
  by the file cap; and the tokens above.
- **Review.** The acceptor's lines, the inheritance drop, the suite refusal
  and the skill refusal are rules validators and planners read; they were
  designed against the incidents above (`2e6bdcfc`, `760fef4c`, the
  seed-inheritance incidents) and reviewed three ways (below). No live run has
  exercised them yet.

## Not built here

- A picker in the viz console. The conversation proposes read runs
  ([below](#read-runs-from-the-conversation-2026-10-17)); the console has no
  control of its own to add or remove one.
- The kernel-enforced read-only mount (d).

## Review 2026-10-17

Three adversarial reviews (security, lifecycle, the text models read) found
no blocker and these defects, each fixed as the owner decided:

1. **Modes.** 0444 copies made restored files read-only and dropped the
   executable bit (rejected shortcut (k)). Copies keep their saved modes; the
   check compares sha256 and mode.
2. **A change put back.** The check compared bytes only, at acceptance: a copy
   rewritten, compared and restored read "byte for byte". The host keeps each
   copy's identity and reports one changed after the copy; deleting or adding
   files no longer reads the same: added names are their own fact.
3. **Retention.** A read run was held only for a queued or running reader, so
   a paused reader kept bytes recorded deleted. Held now while any reader can
   be continued; a finished reader removes its copies.
4. **File count.** 64 MiB admitted 300,000 files: about 16.5 s of event-loop
   stall per admission, and a workspace past the checkpoint's file limit.
   Capped at 10,000 files (the largest saved manifest held 1,502).
5. **Probe inheritance.** The drop missed paths without a trailing slash and
   HTTP stamps, and dropped exclusion commands (rejected shortcut (l)). It now
   drops a path into a copy, id required, in every replayed field.
6. **Preview.** A run that started an older run's server from its copy could
   leave that copy's entry as the delivered run's server. Skipped.
7. **Scaffold.** A seed holding only `.atoma-runs` was "not empty", which
   invited `rm -rf .atoma-runs`.
8. **Parent suites.** The runner's snapshot leaves the copies out, so a suite
   comparing with one could never pass and its child was rejected every round.
   Refused at plan time, every time, with zero tokens.
9. **Host comparison.** The incident's criterion still rested on a model's
   `sha256sum` surviving the root's transport cut, and the read-back could
   spend the acceptor's file budget on a copy. The host now compares the files
   the criteria name, and never reads a copy back.
10. **Guidance.** "Never edit them" invited deleting a copy, and "exclude
   .atoma-runs" conflicted with the TypeScript rule. Rewritten (above).
11. **Skills.** A recipe could carry a run id into the shared catalogue and a
   path one run held. A recipe naming a copy is never learned, revised or
   compiled.
12. **Docs.** "Never carried into a later run" was false for comparison reruns
   and continuations; `cmp` is not on the allowlist; the caps and the
   `rerunOf`/`resumeOf` refusal were missing from `tools/list`.

## Second review 2026-10-17

A second pass over the fixes (verify, regressions) found no blocker, two
should-fix regressions, two should-fix gaps and nits. Fixed as the owner
decided:

- E1. Writable copies lost their guard against the model's write tools,
  which exempt every `.atoma*` path from the blind-overwrite refusal:
  `write_file`, `edit_file` and `atoma-scaffold` now refuse a copy.
- E2. The deepening's archive kept the copies past the read run's retention:
  they are removed before the archive is made.
- E3. A paused run continued never ended again itself, and a restart's
  failed run never ended: their copies are released at the continuation's
  end and at the next boot.
- E4. Two definitions of "can still be continued" (rejected shortcut (n)).
- E5. The host comparison missed `.tsx`, `./x.js`, `/x.js`, `bin/cli`,
  `Makefile` and images: it searches the criteria for the saved paths.
- E6. A whole copy swapped aside and back read intact: directories are
  tracked.
- E7. Commands reaching the copies by a glob or a `cd` were inherited.
- E8. The guidance claimed copies stay out of "every later run".
- E9. The suite refusal said "can never pass".
- E10. A compile example naming a copy stamped the recipe (rejected shortcut (o)).
- E11. Comments still called `--ignore-pattern '.atoma-runs/**'` what the
  guidance asks for; the guidance asks for a copy of the workspace.

## Third check 2026-10-17

A focused check of the second pass found no blocker, three should-fix and
two nits, each fixed as the owner decided:

- F1. A cancelled reader's checkpoint row stayed 'running', so its snapshot,
  copies included, outlived the read run's retention. A released run's
  snapshot loses them too.
- F2. Removing the copies before the deepening's archive failed the restart
  when a shell had made them read-only, where 44fd3757 had deepened. Archived
  first, then removed at best, and every release removes that way.
- F3. Boot released a restart's failed continuation but not the paused run it
  had consumed. Both now, as at a normal end.
- F4. Exclusion spellings were read as paths: `--glob='!…'`, `zip -x`,
  `fd -E`, git `:!` and `:(exclude)` pathspecs, a grouped `find … -prune`.
- F5. The stem rule matched ordinary words ("todo", "notes", "design") and
  took the comparison's slots: only paths spelled out count there.

## Read runs from the conversation, 2026-10-17

The integrated assistant could not carry read runs: its proposals held a goal
and criteria, and `atoma_run_start` refused `readRunIds` beside
`conversationApproval`. Of 384 production project runs that day, 5 came from a
conversation, the four since 10-12 confirmed in the browser, three of them on
Attica. Two goals named an eligible run of their project other than their seed
(`2e6bdcfc` named `50019ee0`, `7d3373ba` named `d49796f8`), both times the
second newest eligible run; Attica had 36 eligible runs of 59.

- **The proposal carries them.** A start proposal takes an optional
  `readRunIds`, one to three (`assistantProposalSchema`). One helper,
  `canonicalAction`, sorts them and drops an empty list, where a proposal is
  saved and on both sides of an approval's comparison. It is not a zod
  transform: the SDK renders `atoma_conversation`'s outputSchema in output
  mode, where `z.toJSONSchema` throws on one. Zod keeps an explicit
  `readRunIds: undefined`, which `isDeepStrictEqual` tells from an absent key:
  without the canonical form, a start without read runs restated that way never
  approves.
- **Readers first.** Conversation bodies and approval receipts are read back
  through strict schemas. The readers (`assistantActionSchema`, which reads the
  list back by spelling, `storedReadRunIdsSchema`, and the confirm request's
  echo) ship one deployment before any writer, so a reverted writer leaves
  every saved conversation readable. Without the writer, a saved start with
  read runs is refused before its approval claims it.
- **Candidates.** `atoma_project_readiness` and its HTTP route list
  `selectableRuns`: at most 8 runs, newest first, among the project's newest
  40, that pass `iterationEligible`, the one rule `iterationBase` and
  `readRuns` refuse by. Each is `{runId, title, status, endedAt, files,
  bytes}`, and the list serves `baseRunId` too. The assistant already reads
  readiness every turn, before the newest run.
- **The assistant.** One sentence in the project prompt (below). The reply's
  read runs must be in the readiness read after the reply, or nothing is
  saved. It does not sum files and bytes, which would be a second definition
  of the caps: approval checks them.
- **The MCP.** `atoma_run_start` takes `readRunIds` beside
  `conversationApproval` as part of the restated action, in both protocol
  eras, through one handler: an omitted, added or different list is refused
  ("restate its readRunIds unchanged") before anything is claimed or
  reserved, and another order is the same list. `atoma_conversation_update`
  checks a proposal's read runs with `ProjectService.checkReadRuns`
  (`ProjectStore.readRuns`: the rule and both caps, from the saved manifests,
  hashing nothing), and approval checks them again before its claim, so an
  expired read run or an exceeded cap leaves the proposal pending, never
  uncertain. Bytes changed on disk are found at admission, after the claim, as
  for any start.
- **The browser.** The proposal card lists each read run: its title from the
  run list the open project already polls, its id's first 8 characters, its
  status and how long ago it ended; an id that list does not hold shows alone.
  One notice says the run gets copies to read, restore from or compare with,
  never delivered or published. Approve echoes the list the card displayed,
  and the server refuses an echo that differs from the saved list ("Reload
  Atoma and review this proposal before approving it"): a tab still running a
  client that never displayed read runs cannot approve them. To change them,
  the person sends a message, as before. Read runs are approved in the
  conversation, the one acceptance surface; the result card and acceptance are
  unchanged, and the copies never appear in the review files.

Text the models read, about 4 characters per token, measured on the built
schemas:

- The project prompt sentence, 324 characters (about 81 tokens), in every turn
  of a project's conversation: "readiness.selectableRuns are earlier runs of
  this project whose saved files a run can be given. Only when the person asks
  to restore, reuse or compare files from one of them, put its runId in
  readRunIds (at most 3) and name those files in the goal and criteria. They
  never change where the run starts, which stays automatic." (The design's
  "(the newest delivered or partial run)" was false for an imported
  repository, which starts from its default branch.)
- The reply schema, in every assistant call: 2,594 to 2,983 characters (about
  97 tokens more), the field's description included.
- `selectableRuns`: at most 8 entries of about 197 characters (about 395
  tokens) in every project turn.
- `tools/list` for a member: about 1,000 characters more (about 250 tokens):
  the field in `atoma_conversation_update`'s input (3,635 to 4,024) and in
  `atoma_conversation`'s output (6,535 to 6,890), the restatement rule in
  `atoma_run_start`'s descriptions (4,580 to 4,717) and `selectableRuns` in the
  readiness description (221 to 337).
- A run approved with read runs pays what [Text the models read](#text-the-models-read) records.

Rejected:

- A picker, or chips the person removes: the browser would author part of the
  action (it confirms ids and versions, never action bodies), which needs a
  new versioned write and its MCP twin, and the ids would drift from the goal
  and criteria, which must name the files the host compares.
- The refusal turned into an override added at confirmation: the person would
  approve what the card never showed.
- Candidates from `atoma_project_runs`: its compact rows lack rerun, expiry and
  manifest facts, a SQL filter would be a second copy of the rule, and
  filtering pages thins them.
- A new MCP tool: a catalogue row for what readiness answers.
- The host picking ids out of the goal or the chat: rejected shortcut (g).
- `baseRunId` in proposals: it changes where the run starts, a decision of its
  own (67 MCP runs used it). It can reuse this mechanism.

Risks that remain:

- Read runs proposed when nobody asked cost tokens and disk. The sentence says
  only on request, the ids come from the host's list, the card shows them and
  the person approves. After shipping, compare the proposals that carry read
  runs with those approved.
- An MCP client that kept `atoma_conversation`'s outputSchema from before the
  readers shipped (a strict start without the field) may reject a read-runs
  proposal. Unverified.
- Run titles are model text. They come only from the same organisation and
  project, grant no access `atoma_run_file` does not already give, and a run
  named because of one still needs the person's approval of the card.
- The assistant proposes only the newest eligible runs; older ones go through
  `atoma_run_start`.
- A very long project brief can still push `selectableRuns` past the
  20,000-character context cut. The newest run no longer does: since the same
  day it reaches the model as its decisive facts, its goal and its files as
  counts and the first paths, never the whole manifest, which alone exceeded
  that cut for Attica's newest delivery (21,733 characters).
