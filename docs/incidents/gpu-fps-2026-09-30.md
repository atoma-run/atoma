# Watching a run on an integrated GPU — measured 2026-09-30

Status: **four fixes shipped, one decision left to the owner.** The owner
reported the app "slow on this machine" while consulting a run, and asked
whether the particle background seen behind the large crystal was still paid
for there. It is not: `ambientRoot` holds nothing on the Runs view (checked on
the live scene graph), as `396442a5` made it. The slowness was elsewhere.

## Machine and method

AMD Ryzen 5 5500U laptop, integrated Radeon (Vega 7), Windows 11, 60 Hz panel,
100 % scaling, on mains power. Chrome for Testing (Puppeteer's) on the WebGPU
backend, cross-checked with the installed Chrome 153 through
`PUPPETEER_EXECUTABLE_PATH` (same numbers). The owner's own tab could not be
driven: no browser-control tool was connected and their Chrome runs without a
debugging port, so every number here comes from a separate profile on the
same hardware, at the owner's geometry: 1920×970 CSS pixels, DPR 1.

Three instruments, all on the compiled client:

- `npm run viz:frame-probe` (the repository tool) for structural counters, and
  with `--unlock` for frame cost.
- Scratch scenarios built on the same fixture: a LIVE run whose trace gains an
  event every 1.5 s while an in-page pointer sweeps the timeline (30 s,
  headful, vsync), and interleaved A/B arms that hide one subtree at a time.
- `viz-gpu-smoke`, run on HEAD and on this change back to back.

Two reading rules, on top of the 2026-09-06 ones (thermal drift, back-pressure):

1. **GPU timestamps under vsync are not costs.** At 60 fps the GPU idles
   between frames and its clock governor drops, so a pass measures longer at
   a light load: identical arms read 6.5 and 15.6 ms twenty minutes apart.
   Measure cost with `--unlock`, where the GPU runs at its top clock.
2. **The rAF interval at vsync hides everything below 16.7 ms.** Every
   scenario of the fixture held 60 fps on a cool machine. What the owner saw
   was the headroom disappearing (heat, other GPU clients) and the stutters
   that no amount of headroom absorbs.

## What was found

| finding | measured |
|---|---|
| Every poll of a LIVE run rebuilt the whole scene | 35 rebuilds in 30 s, p50 22.2 ms, max 60.4 ms; 114 frames over 33 ms |
| `toLocaleTimeString` per card per rebuild builds an `Intl.DateTimeFormat` each call | 22 % of rebuild self time; 0.074 ms per call against 0.0014 ms cached |
| The pointer light re-rendered the whole stage through a screen-sized filter | +1.6 to +3.4 ms per lit frame, unlocked |
| That filter also resampled the stage | text over 300 px from the light changed by up to 113/255 when the pointer entered |
| A finished run's four metric tiles pulsed forever | 48 Graphics updates and a 42.5 KB band upload per frame |
| Crossing the retained Runs window rebuilt mid-gesture | smoke scroll P95 33.8 ms on HEAD |
| MSAA at DPR 1 | Runs idle 6.5 → 3.0 ms, lit 10.1 → 5.0 ms with `?atomaQuality=performance`, unlocked |

The MSAA row corrects the 2026-09-06 record, which found MSAA irrelevant at
1920×1080: that comparison read vsync-locked intervals. Unlocked, it doubles
the frame here. It is not changed: turning it off shows stair-stepping on the
crystal and on rounded outlines at 1×, which is the owner's call.

## What changed

1. **Cached formatters.** `client/date-format.ts` hands out one
   `Intl.DateTimeFormat` per locale and option set; the card clock, the
   bookends, relative dates and project dates use it. Output is identical
   (pinned by `tests/viz-date-format.test.ts`).
2. **A live run's own refresh waits for a still reader.**
   `renderer/live-refresh.ts`: the growing trace of the run on screen, the run
   index and a project's run list while one is live wait while the pointer
   moves or the view scrolls, at most one rebuild a second, never more than
   3 s. Anything a reader causes — a click, a selection, a first trace —
   renders at once; a scroll meanwhile moves the retained window over the data
   on screen.
3. **A bounded pointer light.** On WebGPU, once the far field is detached, the
   light is carried by a childless `lightRoot` whose `blendRequired` filter
   copies the light's reach (twice the halo radius, where the light is below
   0.07 of an 8-bit step at maximum tuning) and adds the light there. The hero
   and the WebGL fallback keep the full-stage filter. Both share one shading
   function and one uniform group; `?atomaLight=full` forces the old carrier
   for an A/B.
4. **Motion means activity.** Metric tiles pulse only for a live run; others
   settle after their entrance. The retained Runs window re-centres in the
   first 400 ms pause after a scroll that used half its overscan.

## After

| Runs idle uploads per frame | 190 KB | 148 KB |
| smoke scroll rebuild P95 (minutes apart, change then HEAD) | 33.8 ms | 23.4 ms |

`viz-gpu-smoke` still fails on this machine, on HEAD as on the change, and on
one assertion only: the scroll P95 budget of 12 ms, calibrated on Metal. Every
behavioural assertion passes; `viz:smoke:gc` passes, and its scenario replayed
on the Runs view with the bounded carrier raised no WebGPU error. The welcome
crystal's P95 moved between the same two runs too (49.9 → 33.4 ms), but its
path did not change: that is the machine, not the code.

## Registered, not built

- The MSAA decision above.
- 150 draws a frame on Runs: every label is its own texture, so batches break
  every sixteen. A label atlas is the lever.
- Teardown is 4.5 ms of a rebuild; destroying the previous scene off the
  critical frame is possible but crosses the retention invariants.
- The bounded light still ends the canvas pass once to copy its reach: one
  extra MSAA resolve per lit frame, the remaining ~1 ms.
