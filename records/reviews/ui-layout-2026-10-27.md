# Platform-admin UI layout review — 2026-10-27

The approved scope was the web application available to a platform admin.
The crystal, 3D navigation icons, lighting, five themes and camera transitions
remain in the existing GPU renderer. Atoma Compute itself and the interiors of
generated applications were excluded. No API, permission or storage contract
changed, and no production run or paid model call was started for this work.

## Implemented composition

`ui-layout.ts` supplies shared spacing, typography and control-size tokens to
Pixi and CSS. View frames now share 24 px titles, 16 px content insets and
measured title/subtitle clearance. Native form overlays derive their origins
from the same frame geometry. The existing camera gutter and compact timeline
geometry remain intentional exceptions to the general spacing scale.

Settings use a 240 px vertical navigation column inside a maximum 1,200 px
frame, or a section selector below 1,024 px. Active panels scroll independently;
long technical values wrap. Announcements have persistent labels, a maximum
960 px reading width, a 160 px initial message field and differentiated actions.
Conversation text is 16 px with a 72-character reading width.

Project headings, section controls and repository links occupy separate rows.
The project overview defaults closed below 1,200 px and respects explicit user
choices. Runs below 600 px place status and essential actions before two closed
summary/filter disclosures. Expanded controls have a bounded scroll region,
leaving the chronology available.

Registry, Skills and Docs show one pane below 900 px of content width. Explicit
selection opens the detail; Back retains the selection and scroll position.
Docs retain separate index/article offsets. Files keep their existing responsive
reader and now share the clearer project framing. Organisation, journal and
ledger rows align related metadata. Journal severity and event-family selects
retain the existing server-filter query contract.

The navigation rail scrolls on short windows instead of shrinking destinations.
Its controls retain 40 px desktop / 48 px handheld rows. The smoke exercises the
rail using physical wheel input and then clicks the revealed canvas destination.
Common form controls, focus outlines and menu surfaces keep their native keyboard
paths. Text contrast is adjusted at style creation, cached by theme/color; no
per-frame contrast calculation or change to 3D materials was introduced.

## Capture evidence

The initial inventory contains 35 production screenshots. The after inventory
contains 50 local states and 1,200 screenshots. The gallery identifies capture
size, camera, theme, language and observed application state. Production and
local fixtures contain different business data, so this is a layout comparison,
not a pixel-diff claim. Invitations and proposals use local fake data only.

Each state has these 24 variants:

- 390, 528, 768, 1,024, 1,440 and 1,920 px, both overview and focus cameras.
- Four additional themes at 1,440 px / focus; Nocturne is in the base matrix.
- French, German (long labels) and Arabic (RTL) at 390 and 1,440 px / focus.
- Reduced motion at 390 px and logical reflow at 720 × 480 / DPR 2.

This is a deliberate set of variants, not the full width × camera × theme ×
language Cartesian product. All 1,200 captures pass the recorded global/native
form overflow checks and fixture HTTP-error checks. Pixel review and the real
browser smoke supplement those measurements: DOM bounds cannot prove every
GPU mask or every arbitrary customer-provided string fits.

The [capture inventory](ui-layout-2026-10-27/capture-inventory.json) records the
50 states, filenames, dimensions and checks. It includes platform, organisations,
announcements, live runs, journal, ledger, Burn-in, Sentinel sections and detail,
Registry/Skills/Docs list and detail, every settings section, project sections,
run activity/result, file reader, preview, account/theme/tuning/notification
menus, invitation, and empty/loading/reconnect/approval assistant states.

The self-contained gallery is stored with this task's local artifacts:
`atoma-ui-audit/index.html`, with `before/`, `after/` and `inventory.json` beside it.
Large image assets are intentionally not added to the source repository.

## Accessibility measurements

Actual Chrome 200% zoom produced a 960 × 468 logical viewport with document
scroll width equal to client width. The keyboard navigation bridge and focused
control remained inside the viewport. The browser zoom was restored afterwards.
See [keyboard and zoom measurements](ui-layout-2026-10-27/keyboard-zoom.json).

The [contrast measurements](ui-layout-2026-10-27/contrast.json) use Chrome pixels
from opaque swatches after the actual CSS theme filters, comparing principal,
muted, label and semantic text colors against all three panel backgrounds.
The minimum ratios are Nocturne 4.6199, Amethyst 4.6301, Aurora 4.5099,
Copper 5.0404 and Snow 5.0450. This meets the 4.5:1 normal-text threshold for
these sampled tokens. It is not a WCAG certification of every dynamic scene,
background, arbitrary content or assistive-technology combination.

References: [Material layout](https://m3.material.io/foundations/layout/layout-overview/overview)
and [WCAG 2.2 contrast minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).

## GPU comparison

Two alternating before/after pairs used the same Chrome, Apple M4 Pro Metal
backend, 1,280 × 800 viewport, DPR 1 and 300 frames per scenario. Vsync was
unlocked. Reference source is main `7627127f`, built with the same dependencies.
Raw evidence: [before A](ui-layout-2026-10-27/frame-probe-before-a-1280x800-dpr1-unlocked.json),
[after A](ui-layout-2026-10-27/frame-probe-after-a-1280x800-dpr1-unlocked.json),
[before B](ui-layout-2026-10-27/frame-probe-before-b-1280x800-dpr1-unlocked.json),
[after B](ui-layout-2026-10-27/frame-probe-after-b-1280x800-dpr1-unlocked.json).

Idle mean intervals were 0.26–0.29 ms before and 0.27–0.28 ms after; both P95s
were 0.4 ms. Timeline-hover means were 0.43–0.48 ms before and 0.44–0.45 ms
after; both P95 ranges were 0.6–0.7 ms. Scroll-rebuild P95 was 5.7–5.8 ms before
and 5.5–5.7 ms after, with zero missed renders in all four samples.

The new frame/rail adds approximately two indexed draws per frame (idle about
44 → 46), while per-frame allocations and texture uploads remain unchanged in
these scenarios. No measurable slowdown appeared here. These small samples do
not establish a universal speedup or performance on every device. GPU timestamp
queries were unavailable, so the reported values are frame intervals and CPU-side
render timings, not isolated GPU execution nanoseconds.

Reproduce with `npm run viz:frame-probe -- --label <label> --width 1280
--height 800 --dpr 1 --unlock --frames 300 --only runs --out <directory>` against
separately built checkouts, with no other browser probes or heavy tests running.
